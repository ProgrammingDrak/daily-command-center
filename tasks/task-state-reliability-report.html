Task state reliability

Rapid reschedules now land in order, stale subtree moves cannot strand nested work, and production is verified on the merged revision.

PR #294 mergedProduction verified2,600 stress assertionsNo schema migration
What was broken

Two moves of the same task could overlap. In one narrow server interleaving, a request rebuilt the subtree from an old day after another move committed, then moved the parent without its children. The visible result was a task that seemed not to stay rescheduled or nested work left behind.

What's fixed

Use the same reschedule controls as before. Moves for one task are now sent in click order, while moves for unrelated tasks remain parallel. If another tab changes the task during the server transaction, the stale plan is rejected before any write and automatically rebuilt once.

How to confirm
  1. Move a task with subtasks to another day. Expected: the parent and every nested task appear together on the destination day.
  2. Move the same task twice quickly. Expected: the second destination wins and remains after refresh.
  3. Complete and un-complete a task, then refresh. Expected: the final state remains exactly as selected.
Who's affected

Anyone using the itinerary, carryover review, calendar placement, or completion-date flow benefits. There is no new UI to learn and no recovery step required.

Summary

The fix closes the remaining race between route-level subtree discovery and transaction-level row locks. It also prevents rapid same-task clicks from racing each other in one browser tab.

Before and after

Before

Request A reads Monday. Request B moves the full tree to Tuesday. Request A queries Monday, sees no children, and can move only the parent to Wednesday.

After

The transaction locks the parent and compares its date and version to the route snapshot. Any mismatch rolls back before a write, then the client retries from current state.

Production database impact

No DDL, migration, backfill, or destructive SQL was added. db.js changed only the existing reschedule transaction: after SELECT FOR UPDATE it compares the route's expected date and updated_at value with the locked row. A mismatch throws RESCHEDULE_STALE and rolls back.

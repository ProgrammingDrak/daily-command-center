# Event-linked Android alarms — local review candidate 0.5

The full **Alarms** page is `/public/alarms.html`, reached from the Android alarm panel or an event's detail editor. Native Device alarms remains an offline full-screen list/editor for independent and linked definitions. During DCC scheduled-event creation, an explicit checkbox and 0–1440 minute offset can propose a linked alarm **after** the saved block is read back from the server. Failed/offline event persistence never pretends the phone alarm was saved. The event remains saved if subsequent alarm review fails.

Links use **workspace ID + acknowledged block ID**, never a title/local presentation ID. Duplicate labels are safe. This iteration creates one disabled local phone definition per saved event occurrence; native review merges it into existing definitions, preserves independent alarms, and requires confirmation. It refuses replacement while a quiz is pending. Creating the definition does not enable it or request permissions. Configure math/quiz, difficulty and count on the page, then review/enable in native Alarms. Event details show link, offset, enabled definition, next local delivery and last DCC refresh when the phone reports them. Unknown phone state is visibly unknown.

## Timing and state rules

- Default offset is zero (event start). Explicit offsets subtract elapsed minutes from the resolved timestamp, including across midnight/DST. Offset-bearing event timestamps remain absolute when device timezone changes. Floating saved DCC date/time uses the configured DCC event timezone (`DCC_APP_TIME_ZONE`), not the phone timezone. DST gaps move forward; folds choose the earlier instant. Native scheduling uses this absolute instant, while independent alarms retain their device-local wall-time policy.
- The Android WebView refreshes known links every minute while visible/online and on reconnect/return; the Alarms page also has a manual refresh. Read-only requests use existing session authentication and workspace ownership. Late replies after logout are canceled, and workspace is rechecked before bridge updates. Native ignores unknown links, wrong scopes and older snapshots. No new calendar account grant, provider call or external event mutation is added.
- A successful DCC snapshot refresh updates the event timestamp/offset link and reconciles the native OS alarm. One consumed occurrence key survives rescheduling, reload, recovery and clock changes, so the same event alarm cannot ring twice. An active quiz keeps its original questions/progress; a reschedule does not reset it.
- A positively confirmed cancellation/deletion pauses and **disables** that link. Cancellation stops its pending quiz/audio safely. Independent definitions survive. A recovered event can update the link but never silently enables it again. A missed or consumed event occurrence is not replayed after moving it into the future.
- Offline/network/permission failures retain the last snapshot without pretending the event was deleted. **24-hour warning threshold, not a delivery cutoff**: enabled alarms remain armed at the last confirmed event time even without opening DCC daily. Old snapshots warn that offline/remote changes may be unknown and show the last successful refresh. Age and a clock rollback never suppress delivery. The historical `validUntil` field remains in stored snapshots only as a backward-compatible warning timestamp. Delivery still requires native readiness and an unconsumed, enabled occurrence.
- Realtime Google Calendar sync is explicitly disabled in current DCC source (`routes/gcal.js` calendar-data routes return 410). Calendar entries are materialized into dated DCC blocks by existing ingestion. A refresh reads DCC's latest saved block; it does **not** force Google to update it or prove provider freshness. UI names this distinction. A Google-side reschedule/deletion may remain unknown until DCC ingestion catches up, even when the phone is online. Do not promise Google-side live synchronization.
- Recurring-series creation is out of scope: choose a specific persisted dated occurrence. No guessed RRULE expansion, future-series alarm, all-day/untimed alarm or external event creation. A later series feature needs an explicit instance/series decision and source recurrence semantics. Existing calendar permissions remain unchanged.

Synthetic tests cover stable identity, timezone/DST/offsets, invalid values, wrong workspace, rescheduling, duplicate delivery, stale scheduling/delivery retention, cancellation during quiz, recovery without enabling, and independent alarms. ## Debug signing versus release identity

A **debug-signed** APK is valid for private developer testing; a Play Store/public release is unnecessary. Only file metadata was checked at the usual `~/.android/debug.keystore` and isolated `ANDROID_USER_HOME/debug.keystore`; neither exists. No key content was searched/read. This project deliberately has debug signing disabled to prevent Gradle silently generating a credential, so no current signed debug shortcut exists.

With separately approved signing, native-only testing could use a dedicated debug/test identity. Debug builds expose a debuggable app; their keys are unsuitable for long-term release ownership. Losing/changing a signer breaks in-place updates and can require uninstalling phone-local alarms. A separate debug package avoids overwriting a release install but needs a debug-specific manifest/package and server association/config; this is not currently implemented.

Verified HTTPS Google login requires the **actual installed package and certificate fingerprint** in Digital Asset Links for either debug or release. Current native/server config fixes `com.drake.dccalarm` and one approved certificate; a debug package suffix is not an automatic bypass. No additional Google native client is required, but signed app association, reviewed server routes, deployment topology and live browser/device interoperability remain pending. A stable Drake-owned release identity is still a sensible path for a daily-use pilot; first debug testing is a valid alternative if he approves that tradeoff and key custody.

Official sources: [Android signing and debug certificates](https://developer.android.com/studio/publish/app-signing), [App Link association](https://developer.android.com/training/app-links/configure-assetlinks), [Auth Tab verification](https://developer.chrome.com/docs/android/custom-tabs/guide-auth-tab).

## Corrected loss-of-sync policy (0.5 supersedes 0.4)

Version 0.4 incorrectly used freshness as a delivery cutoff. Do not distribute that candidate. Version 0.5 keeps enabled, previously confirmed future event alarms scheduled across stale data, offline use and reboot. The web/native UIs separate definition **Enabled** from actual **Armed on this phone**, **Delivery pending**, or **Not armed** state; last-refresh and stale warnings do not claim the event source is current. Native readiness failures still prevent arming, and device permissions are never automatically granted.

Missing/404 or denied access does not prove cancellation. A new authenticated, workspace-owned, read-only `/api/blocks/:id/alarm-state` lookup can positively return an owned tombstone. Only a positively received deletion/cancellation disables the link. Missing rows, purged records, auth errors, malformed events and network failures retain the last confirmed timing and warn; there are no external provider requests or event writes. A tombstone confirms deletion even when its old timing fields are absent. Reconnection updates future schedules or applies a confirmed cancellation; it never silently re-enables a disabled/consumed link.

The existing late-delivery policy remains explicit: a real previously armed OS trigger delivered within **60 seconds** of its intended time is accepted once, regardless of snapshot age. Foreground/status refresh during that window preserves the pending event delivery instead of canceling it. A trigger more than 60 seconds late is recorded missed; it does not cause a catch-up alarm. Boot/clock-change recovery schedules future occurrences only and skips/records past ones without audio. Already-started quizzes are not reset by a timing refresh; duplicate occurrence delivery stays blocked. Linked recurrence stays one persisted occurrence; independent repeat-day alarms are unchanged. These limits avoid unexpected alarm storms, but cannot prove actual OEM/locked/reboot delivery before physical-device QA.

Tradeoff: offline or ingestion-delayed event reschedules/cancellations may cause the alarm to ring at the **old confirmed time**. That is deliberate and visible; lost synchronization alone no longer creates a missed alarm. Google realtime sync remains disabled, so an online phone refresh cannot force Google-side changes to appear before DCC ingestion. No behavior-changing release/signing/install/permission or real-alarm action was performed.

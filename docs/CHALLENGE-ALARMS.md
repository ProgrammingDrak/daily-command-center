# DCC challenge alarms — phase one

Branch `feat/challenge-alarm`, based on `f845ad6`. Worktree: `.worktrees/feat-challenge-alarm`.

The DCC web feature remains a **browser prototype**. A unified Android app containing DCC's web UI and offline native alarms is now included in `native-alarm/`, with a verified unsigned APK build and simulated state tests. It has not been installed or tested on a phone. No production database write, deployment, push service, signing key, or device permission grant is included. Sleep tracking and health analytics are outside this phase.

## Existing platform and decision

DCC is Express with modular browser JavaScript, a standalone PWA manifest, and a separate Ink service worker. Inspection found no Android/Gradle/Kotlin/Capacitor project. Installing the PWA or wrapping it in a WebView alone does not provide a native alarm scheduler.

Chrome throttles chained timers in hidden pages, in some cases to checks once per minute. There is no dependable wake-up contract for this browser implementation when locked, backgrounded, suspended, closed, or rebooted. We do not use web timers or network push as an Android wake-up mechanism. [Chrome timer documentation](https://developer.chrome.com/blog/timer-throttling-in-chrome-88).

The approved minimum mobile path is one Android app wrapping DCC’s existing dashboard, with its own native alarm/challenge screen and scheduler. DCC can continue to provide dashboard configuration, but the phone must persist and acknowledge each definition locally before DCC labels it scheduled on that phone. The alarm must work offline without a web session or server. The unified app is implemented and builds as an unsigned APK; native OS/device delivery has not been tested. See [Android app](../native-alarm/README.md) for implemented behavior and remaining device checks.

## Prototype behavior

- Header entry remains visible on mobile and shows the next enabled browser occurrence, pending challenge, or snooze.
- Up to 20 definitions: one-off local date/time, or selected weekdays; enable/disable, edit, and remove.
- Math or number quizzes, three difficulty levels, 1–10 correct answers. The current question, progress, and definition snapshot persist together.
- IndexedDB stores definitions, pending challenges, the occurrence ledger, and checkpoint in one transaction. A failed save stops scheduling and reports failure. Invalid stored data is preserved and fails closed.
- A visible-page session starts only on an explicit button press. The Web Locks lease permits one scheduler per browser profile/origin. Unsupported or denied coordination disables scheduling. Closing/reloading stops the session. Definitions alone do not arm browser background alarms. An explicit JSON export/import is available for the DCC Android app; DCC never labels an export as phone scheduling acknowledgement.
- One occurrence key per definition and local calendar date prevents duplicate ticks, repeat-hour duplicates, and clock-back replay. Different alarms due together queue; one challenge is displayed at a time. A correct answer count completes one occurrence, not future repeats. Emergency stop is recorded separately from completion.
- Optional one five-minute snooze preserves quiz progress. Disabling/removing a definition cancels its pending/snoozed challenges. Editing a pending definition requires stopping it first.
- Esc, Close, or backdrop pauses a saved challenge and stops sound. Reopen to resume. Emergency stop skips the quiz and consumes the occurrence. The quiz never traps the user into audio.
- Two synthesized tones and a capped volume slider; sound starts only from **Preview sound** or **Play sound**, and stops after four seconds. There is **no automatic ringing** in this prototype. Visibility changes, closing, snooze, and emergency stop close audio immediately. Blocked audio leaves visual dismissal usable.
- Scheduled visual challenges require the page visible, device awake, and a running session. Alarms more than 60 seconds late or observed hidden are marked missed, never replayed as surprise sound. A pending challenge already saved can resume silently after reload. Without a session, missed-state reconciliation waits until the next explicit session start.
- Device-local wall time is intentional: travel/timezone changes follow the device. Spring DST gaps move forward by the gap (02:30 becomes 03:30 for a one-hour gap); fall folds choose the earlier offset and fire once. Consumed local dates stay consumed after timezone changes. A large forward clock jump skips stale alarms. Browser snooze uses wall-clock milliseconds, so clock changes can shorten/extend it.
- Alarms belong to the device browser profile, shared across DCC accounts on that profile. This is explicit in the UI. No task state is reused, no remote convergence is claimed, and there is no account alarm sync. The page itself has no new offline cache: local records survive offline, but reopening the complete app offline is not guaranteed. Browser eviction/site-data clearing can remove records; no persistent-storage permission is requested.

Native date/time inputs opt out of the shared wheel's automatic enhancement with its documented `data-tw-skip` attribute to retain direct keyboard entry and exact-minute validation. Dialog lifecycle/focus/inert behavior comes from `DCC.overlay`; visual styles use existing DCC tokens. Form labels, live feedback, invalid-answer semantics, large controls, keyboard submission, and emergency dismissal are included.

## Native implementation contract

1. **Local authority:** SQLite definitions and occurrence records, independent of DCC task tables and login. Immutable occurrence IDs, persisted quiz questions/progress, atomic transitions `scheduled → ringing → snoozed/ringing → completed|emergency-stopped|missed`. Scheduling edits and OS cancellation must reconcile idempotently. DCC only displays "Scheduled on this device" after the phone returns local commit + OS scheduling acknowledgement.
2. **Exact delivery:** schedule each next occurrence with `AlarmManager.setAlarmClock(AlarmClockInfo, immutable explicit PendingIntent)`; do not use Android repeating alarms for exact weekday schedules. After receiving/consuming an occurrence, calculate the next local wall time and schedule one next event per definition. The receiver validates enabled state, occurrence identity, and capability before starting the alarm service. Exact alarms can operate beyond the process lifetime; this is the relevant Android platform mechanism. [Android alarm scheduling](https://developer.android.com/develop/background-work/services/alarms).
3. **Action-time consent:** use `SCHEDULE_EXACT_ALARM`, check `canScheduleExactAlarms()` before scheduling, and explain/open system settings only after the person asks to enable the phone alarm. Newly installed apps targeting recent Android versions may lack this access. Revocation cancels pending exact alarms; detect on resume and show "Unavailable" instead of silently falling back to a dependable-looking inexact alarm. `USE_EXACT_ALARM` is policy restricted and must not be added without eligibility review. No blanket battery-exemption request. [Android 14 exact-alarm changes](https://developer.android.com/about/versions/14/changes/schedule-exact-alarms).
4. **Lock screen and safety:** native notification channel/category for alarms, action-time notification approval, and `canUseFullScreenIntent()` capability check. Provide a native accessible Activity for quiz dismissal, with lock-screen presentation only where permitted, plus a notification emergency-stop action. A denied full-screen capability gets an explicit reduced-capability state; do not promise lock-screen takeover. Foreground alarm audio uses appropriate service declarations, audio focus and `AudioAttributes.USAGE_ALARM`, respects system alarm volume/DND and channel settings, and has an emergency action plus a bounded safety timeout. Never force device volume or require solving to stop audio. [Full-screen restrictions](https://developer.android.com/about/versions/14/behavior-changes-14#secure-fsi), [notification permission](https://developer.android.com/develop/ui/compose/notifications/notification-permission).
5. **Recovery:** re-register from local storage on boot, exact-access grant, package replacement, manual clock change and timezone change. For alarm delivery after reboot **before first unlock**, use a direct-boot-aware receiver and device-protected storage for the minimum alarm/challenge facts, with no account credentials. Choose/document gap/fold policy matching the prototype. Boot and clock broadcasts recompute one future occurrence per definition and preserve the consumed ledger; never play a backlog. Native snooze must measure elapsed time and reconcile clock changes rather than inheriting browser wall-time behavior. [Boot recovery and clock types](https://developer.android.com/develop/background-work/services/alarms), [Intent broadcast reference](https://developer.android.com/reference/android/content/Intent#ACTION_LOCKED_BOOT_COMPLETED).
6. **Honest limits:** `setAlarmClock()` is the platform's visible alarm mechanism and is allowed through Doze. That does not establish universal delivery across OEM battery controls or users disabling access. Power-off cannot ring. Android 15 force-stop cancels pending intents; reopening is required to recover. Swipe-away/process death differs from force-stop and needs device testing. An alarm app in locked Android Private Space also cannot operate. [Doze behavior](https://developer.android.com/training/monitoring-device-state/doze-standby), [Android stopped-state behavior](https://developer.android.com/about/versions/15/behavior-changes-all#stopped-state).

The Android app implements a narrowly scoped origin-restricted bridge for status, opening the native alarm screen, and reviewing definitions. The native scheduler and challenge screen remain authoritative. The native toolbar and editor work offline and do not require deploying this branch’s web changes. Inside the shell, the web prototype scheduler is disabled, including when the bridge is unavailable. Logout/account switches preserve device-local alarms explicitly. See the Android README for bridge, navigation, auth and maintenance details. No paid service, credentials, or cloud push dependency is needed.

Before describing native delivery as supported, test real target phones: locked/offline, Doze, process kill/swipe-away versus force-stop, reboot before/after unlock, DST gap/fold, timezone/manual clock changes, exact/full-screen/notification access denial and revocation, battery saver/OEM restrictions, system volume/DND, missing ringtone/audio-focus interruption, duplicate broadcasts, concurrent definition edits, snooze, emergency stop, and TalkBack. The current web QA proves none of those device guarantees.

## Validation and review

Model tests: `node --test alarm-model.test.js` — 14 tests cover scheduling, enabled state, repeat weekdays, bad dates/counts, late/hidden/closed delivery, reload, duplicate ticks, backward/forward clocks, simultaneous definitions, invalid answers, completion, snooze bounds, emergency stop, DST gap/fold, timezone changes, and corrupt state.

Final web result: 31 browser checks and 46 model/relevant UI regression tests pass on portable Node 22.20.0. Native result: unsigned API-35 APK builds, 14 JUnit/Robolectric state/denial/security/lifecycle tests and nine pure-Java synthetic clock checks pass, and Android lint completes. No real device alarms or audio ran. Android lint has zero errors and 37 warnings, primarily localization. Changed JavaScript syntax/lint and whitespace checks pass.

Browser QA uses the existing **database-free** `scripts/ui-review-server.mjs` on loopback port 8199, disposable headless Chrome profiles, a synthetic clock, and fully mocked audio. Screenshots and check results live outside the checkout in the task's `alarm-evidence/` folder. The QA script is included as `scripts/verify-challenge-alarms.mjs`; it rejects non-loopback review URLs, mocks all sound before page load, and never logs in or grants device permissions. Keyboard and ARIA semantics are verified; this does not substitute for a human screen-reader/TalkBack session.

Nothing is deployed, merged, or written to the DCC production database. The Android app needs signing/install approval and real-device validation before it can be relied on as a wake-up alarm. Native snooze is currently disabled; the optional bounded browser snooze remains prototype-only. Browser chime/pulse tones use the system alarm ringtone in the Android app.
